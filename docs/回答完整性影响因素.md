# 回答完整性影响因素

> 本文档梳理 KB_QA 系统中所有影响**回答完整性**（检索是否全面、答案是否充分）的可调参数和代码逻辑，供调优参考。
>
> 完整答案 ≈ 检索到足够多的相关片段 + LLM 正确利用这些片段合成答案

---

## 一、检索阶段参数

这些参数控制**能召回多少候选片段**，是回答完整性的基石。

### 1.1 `vector_top_k` / `bm25_top_k`

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `vector_top_k` | **200** | 从向量Survey结果中取前N条用于后续处理 |
| `bm25_top_k` | **200** | 从BM25 Survey结果中取前N条用于后续处理 |

- **影响**：值越大，召回越全面，但后续LLM合成消耗的tokens越多。
- **旧版参考**：旧版可工作存档使用 `vector_top_k=1000, bm25_top_k=1000`，最终 `used_base_ids=1177`。
- **注意**：实际使用的值由 CLI 从 `KBQADefaults` 读取，可通过 `--vector-top-k` 覆盖。

### 1.2 `vector_score_threshold` / `bm25_score_threshold`

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `vector_score_threshold` | **0.31** | 向量检索相关性阈值 [0-1]，低于此值被过滤 |
| `bm25_score_threshold` | **11.0** | BM25检索相关性阈值，低于此值被过滤 |

- **影响**：阈值越低，通过过滤的片段越多，但噪声也可能增多。
- **旧版参考**：旧版使用相同的 `0.31` / `11.0`。

### 1.3 `vector_survey_top_k` / `bm25_survey_top_k`

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `vector_survey_top_k` | **1000** | 向量Survey阶段top_k，仅用于全面性评估 |
| `bm25_survey_top_k` | **1000** | BM25 Survey阶段top_k，仅用于全面性评估 |

- **影响**：Survey值决定了"预估相关段总数"的计算准确性。`comprehensiveness_ratio = used_base_count / survey_total_relevant`。
- **注意**：Survey结果中实际取前 `vector_top_k` / `bm25_top_k` 条用于后续分析。

### 1.4 `context_window`

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `context_window` | **10** | 基段前后各扩展多少条**同直播同类型**片段作为上下文 |

- **影响**：值越大，每个基段周围的语境越完整，但候选总量会膨胀到 `used_base_ids × (context_window × 2 + 1)` 的量级。
- **旧版参考**：旧版使用 `context_window=10`，最终 `candidate_count=13345`。

## 二、合并策略参数

向量和BM25检索结果如何合并，直接影响最终使用的基段数量。

### 2.1 `max_base_segments`

| 位置 | 默认值 | 说明 |
|------|--------|------|
| `qa.py` → `ask()` → `retrieve()` | **500** | 合并后基础段数量上限 |

- **影响**：控制最终进入上下文扩展的基础段上限。值越大，BM25补充越多。
- **历史bug**：旧版公式 `min(30, (max_base_segments or 200) - len(merged_ids))` 当 `len(merged_ids) > max_base_segments` 时产生负数，导致**BM25补充完全失效**。已修复为 `max(0, ...)`。

### 2.2 BM25 Supplement Limit（代码逻辑）

在 `qa_retrieval.py` 的合并步骤中：

```python
bm25_supplement_limit = (
    80 if len(merged_ids) == 0          # 向量未找到：多补充一些 BM25
    else max(0, (max_base_segments or 500) - len(merged_ids))  # 补充到上限
)
```

- **影响**：控制BM25-only片段补充数量。当向量已找到大量片段时，BM25补充量 = `max_base_segments - len(vector_ids)`。
- **旧版参考**：旧版archive的 `max_base_segments=null`，所有BM25片段全部补充（`used_base_ids=1177`）。

### 2.3 锚点（主播讲话）分数提升

| 检索方式 | 提升倍率 | 说明 |
|---------|---------|------|
| 向量 | **1.1×** | 主播讲话片段的向量得分提高10% |
| BM25 | **1.2×** | 主播讲话片段的BM25得分提高20% |

- **影响**：提升主播讲话片段的排序优先级，有助于更多主播相关片段进入top_k。
- **位置**：`qa_retrieval.py` 的 `retrieve()` → 锚点boost阶段。

## 三、LLM Prompt 约束

Prompt中的限制条件直接决定LLM输出的答案颗粒度。

### 3.1 分组合成 Prompt（`build_group_synthesis_prompt`）

| 约束 | 值 | 说明 |
|------|-----|------|
| evidence 条目数上限 | **≤ 10 条** | 每组证据不超过10条，超出则可能丢失信息 |
| 引用格式 | `[#N]` | 紧贴所支持的分句之后 |
| reason 字段要求 | 注明"主播自述"/"主播转述" | 影响答案的可靠性判断 |

- **位置**：`kb_qa/qa_prompts.py` → 分组合成prompt。

### 3.2 最终答案合并 Prompt（`build_merge_prompt`）

| 约束 | 值 | 说明 |
|------|-----|------|
| 回答字数上限 | **500 字** | 超出会被截断，导致信息丢失 |
| 引用格式 | `[#N]` | 一个中括号内只能有一个编号 |

- **位置**：`kb_qa/qa_analysis.py` → `build_merge_prompt()`。
- **影响**：当多个视频分组都有高质量答案时，500字可能不足以完整综合。

### 3.3 BM25 查询改写 Prompt

| 约束 | 说明 |
|------|------|
| 高频嘉宾名过滤 | 强制保留除"陈嘉仪"外的所有人名 |
| 疑问词去除 | 去掉"为什么""什么"等无意义疑问词 |
| 4-path 联想 | 允许模型联想主题的近义词和具体情况 |
| 输出限制 | ≤ 50字，≤ 200字思考过程 |

- **影响**：过度过滤会丢失关键检索词，导致BM25召回不到相关片段。人名过滤规则尤其关键。

### 3.4 向量查询改写 Prompt

| 约束 | 说明 |
|------|------|
| 保持语义完整性 | 输出完整句子而非关键词 |
| 无高频词过滤 | 不做人名过滤（与BM25不同） |

## 四、其他关键参数

### 4.1 `analysis_batch_size`

| 位置 | 默认值 | 说明 |
|------|--------|------|
| `qa.py` → `ask()` | **20** | 分组合成时每批交给LLM的片段数 |

- **影响**：值越大，单次LLM调用包含的片段越多，但上下文太长可能影响准确率。目前方案C已跳过有用性分析。

### 4.2 `synthesis_context_window`

| 位置 | 默认值 | 说明 |
|------|--------|------|
| `qa.py` → `ask()` | **6** | 合成时每个片段前后各取N条作为局部上下文 |

- **影响**：为分组合成提供额外的局部语境，但与检索阶段的 `context_window` 不同。

### 4.3 `max_retries`（引用一致性校验）

| 位置 | 默认值 | 说明 |
|------|--------|------|
| `qa.py` → `_process_video_group()` | **5** | 引用校验失败时的最大重试次数 |

- **影响**：重试次数越多，越可能获得合规的答案格式，但也增加API消耗。

### 4.4 `call_llm_json` 参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `max_retries` | **5** | JSON解析失败时的重试次数 |
| `max_tokens` | **None**（不设上限） | 输出token上限，设为过低会导致JSON被截断 |
| `temperature` | **0** | 保证可复现性 |
| `response_format` | **json_object** | 强制JSON输出 |

## 五、性能与完整性权衡

| 参数 | 调大效果 | 调小效果 |
|------|---------|---------|
| `vector_top_k` / `bm25_top_k` | 召回更全面，API tokens增加 | 可能遗漏关键片段 |
| `context_window` | 语境更完整，candidate_count膨胀 | 片段孤立，缺乏上下文 |
| `max_base_segments` | BM25补充更多，基段更多 | 向量主导，BM25被压制 |
| evidence ≤ 10 | 答案更简洁 | 可能遗漏部分证据 |
| merge answer ≤ 500字 | 保持简洁 | 信息不完整 |
| BM25 supplement formula | 决定BM25是否被有效利用 | 负数bug导致BM25补充=0 |

## 六、调试检查清单

如果某问题的回答不完整，按此顺序排查：

1. **检查存档JSON** → 看 `retrieval.used_base_ids` 和 `retrieval.candidate_count`
   - 如果 `used_base_ids` 很小（< 50）：`vector_top_k` / `bm25_top_k` 太小，或阈值过高
   - 如果 `used_base_ids` 远小于 `raw_merged_ids`：BM25 supplement被限制
2. **检查BM25查询改写** → 看 `retrieval.bm25_query`
   - 是否丢失了关键实体词？检查BM25 prompt的人名过滤规则
3. **检查向量查询改写** → 看 `retrieval.vector_query`
   - 是否偏离了原问题的语义？
4. **检查分组合成evidence数** → 看 `batches[].evidence` 长度
   - 是否总是10条？可能是 evidence ≤ 10 的限制在截断
5. **检查最终答案长度** → 看 `answer` 的字符数
   - 是否总是接近500字？可能是 merge 的500字限制在截断
6. **检查全面性比率** → 看 `retrieval.comprehensiveness.ratio`
   - 比率越低，说明遗漏的潜在相关片段越多

## 七、Token 优化：用更少的检索达到同样的回答质量

> 实际测试验证：针对"为什么给狗起名顺顺？"，将 `vector_top_k=200, bm25_top_k=200, context_window=10` 降至 `vector_top_k=40, bm25_top_k=40, context_window=3`，**仍能正确回答**，且Token消耗降低 **81%**。

### 7.1 核心发现

| 发现 | 说明 |
|------|------|
| **被引用片段大多是扩展来的** | 13个被引用片段中只有 **3个是BASE**（直接命中），其余10个来自上下文扩展 |
| **BM25是关键** | 3个BASE片段全部由BM25发现（rank 15/38/79），向量在top 200中一个都没找到 |
| **关键片段排名不高** | 最核心的"顺利的顺"在BM25 rank **38**，不是top 10 |
| **更多数据≠更好答案** | 完整参数(200/200/10)只找到吉祥寓意，最小参数(40/40/3)反而找到了反讽+吉祥双重含义 |

### 7.2 Token消耗实测对比

| 指标 | 完整参数 (200/200/10) | 最小参数 (40/40/3) | 节省 |
|------|----------------------|-------------------|------|
| 输入 tokens | 503,092 | **84,653** | **83%** |
| 输出 tokens | 32,084 | **18,315** | **43%** |
| LLM调用次数 | 74 | **30** | **59%** |
| 总 tokens | 535,176 | **102,968** | **81%** |
| base segments | 366 | **69** | **81%** |
| candidates | 6,136 | **445** | **93%** |

### 7.3 为什么更少的片段反而给出了更丰富的答案？

- **信噪比提升**：候选越多，杂音越多。当给LLM塞入6136个candidates时，其中大量是只含"顺"字的噪声（如"顺顺狗界美男子"、"顺顺是只聪明小狗"），LLM需要从大量噪声中筛选信号。
- **关键片段被稀释**：366个base中只有3个真正相关，其余363个虽然含"顺"或"狗"但对回答"起名原因"没有贡献。
- **diminishing returns**：top 40 BM25已经包含了回答所需的全部关键信息，多出的160个BM25结果只是冗余。

### 7.4 优化建议

```
推荐「经济型」配置（平衡质量与消耗）：
  vector_top_k    = 40    # 语义补充，不需要太大
  bm25_top_k      = 50    # BM25是主力，稍微放宽以覆盖rank 30-50的关键命中
  context_window  = 5     # 足够捕获关键片段周围的完整语境
  max_base_segments = 100 # 限制总量，防止BM25过度补充

预期效果：
  base ≈ 80-100
  candidates ≈ 500-900
  tokens ≈ 完整版的 20-30%
```

### 7.5 调优策略决策树

```
回答不完整？
├─ 检查 used_base_ids
│   ├─ 很小 (< 30) → 增大 top_k
│   └─ 中等 (30-100) → 检查答案是否用了上下文
│       ├─ 答案只用了1-2个片段 → 增大 context_window
│       └─ 答案用了多个片段但质量差 → 检查prompt
├─ 检查 BM25 查询改写
│   ├─ 丢失了关键实体 → 修改BM25 prompt的人名过滤规则
│   └─ 查询正确 → 检查 top_k 是否覆盖了关键片段的排名
└─ tokens超标？
    ├─ base > 200 → 减小 top_k 或 max_base_segments
    ├─ candidates > 3000 → 减小 context_window
    └─ 都低但tokens高 → 检查是否多个视频分组，考虑合并策略
```
